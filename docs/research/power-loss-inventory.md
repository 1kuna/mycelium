# Power-loss write-path inventory

## Coverage and limits

**Unverified first:** no power cut, kernel panic, filesystem fault injection, live
queue, database, spool, fleet or NAS inspection was performed. Installed versions,
mount options, drive caches, controller guarantees and backup durability remain
unknown. No tests or gates were run. This is source research for acceptance
criterion 1 of [#1179](https://github.com/1kuna/mycelium/issues/1179), not evidence
that criteria 2–4 pass.

Reviewed source baseline: `7663d789b7134ca907ebb46a6a9bcadf4f261be9`, with
`modernc.org/sqlite v1.39.1`, `tusd v2.9.1` and Go `1.25.6` from
[go.mod](../../go.mod). Primary-source retrieval: 2026-11-09. The research serves
the decision **which durability fixes to implement first**. Evidence that would
change a verdict includes a missing caller-side barrier, different dependency
semantics, or a reproducible crash image demonstrating recovery or loss.

The corpus is the storage-producing code in `internal/myce`, `internal/hostbridge`,
`cmd/myce`, the Python client, examples, installer/bootstrap scripts and local gate
helpers. A sink ledger included file writes, publication/removal helpers, SQL
calls and false positives. A second pass included interface-backed writes,
`os.Root` operations, Python `open`/`replace`, shell copies/redirections and
Windows setup/registry operations. The tables account
for durable state families, their publication/removal paths, and deliberately
ephemeral output. This is a write-path review, not an every-line review of all
repository code. Arbitrary payloads, package managers, Docker's storage engine,
service managers and backup tools have separate durability boundaries, marked
unknown below; their implementations were not audited.

**Evidence labels:** **C** = inspected code; **D** = documented upstream or product
contract; **I** = inferred crash consequence, not reproduced. Every inventory row
contains C/D evidence and an I failure analysis. No row claims observed crash
behavior. Likelihood terms below are qualitative exposure assessments; there are
no measured failure rates.

**Verdicts:** **safe** means the inspected path preserves its last acknowledged
durable state, under working filesystem/device flush semantics and already-durable
ancestors. **Unsafe** means a concrete missing barrier, partial final-name write,
or missing recovery transaction violates #1179. **Unknown** means source alone
cannot establish the guarantee. `K` means `kill -9` of the writer while the kernel
and storage remain running; `P` means sudden power loss **or kernel panic**, both
of which can discard unflushed state. A panic need not drain filesystem caches.
An in-progress, unacknowledged update may recover as old or new; that is not
itself corruption. A successful response must not precede its durability boundary.
Fresh-directory failures in R1 apply across otherwise-safe rows.

The binding product promise is in the [power/network-loss section of the approved
design](../design-proposal.md#L138): no loss of acknowledged intent, no
uncertainty treated as release. [Checkpoint rules](../files.md#resumable-jobs)
require file flush, atomic publication and directory flush.
[MY-03/MY-35](../DECISIONS.md) currently favor fixing forward and explicitly exclude
automatic rollback machinery. #1179 also requests resumable installer rollback;
implementing that cross-file recovery policy needs an explicit reconciliation of
those requirements. Per-file atomic replacement needs no such product decision.

## Primary durability semantics

| Source | Documented fact and consequence for this inventory |
| --- | --- |
| [SQLite `synchronous`](https://sqlite.org/pragma.html#pragma_synchronous), [WAL](https://sqlite.org/wal.html#performance_considerations) | **D:** WAL + `FULL` syncs the WAL on each commit. `NORMAL` omits the per-commit WAL sync: SQLite remains consistent under its filesystem assumptions, but recently committed transactions can roll back after power loss/hard reboot. `NORMAL` remains durable across application crashes. Mycelium currently selects **FULL**, not NORMAL. Do not weaken it as a write-volume optimization. |
| [SQLite `fullfsync`](https://sqlite.org/pragma.html#pragma_fullfsync), [`checkpoint_fullfsync`](https://sqlite.org/pragma.html#pragma_checkpoint_fullfsync) | **D:** both default off. On macOS, `fullfsync=ON` uses `F_FULLFSYNC` for sync operations, including checkpoints; enabling only `checkpoint_fullfsync` does not fix commit durability. `synchronous=FULL` and `fullfsync` are different settings. |
| [SQLite WAL checkpoint ordering](https://sqlite.org/wal.html#checkpointing), [automatic checkpoint API](https://sqlite.org/c3ref/wal_autocheckpoint.html) | **D:** checkpointing syncs WAL before copying into the database and syncs the database before WAL reuse. The default automatic threshold is 1,000 pages. Interrupted checkpointing is part of SQLite's recovery protocol, not grounds to delete WAL/SHM manually. |
| [SQLite atomic commit assumptions](https://sqlite.org/atomiccommit.html#_hardware_assumptions), [SQLite testing](https://sqlite.org/testing.html#crash_testing) | **D:** SQLite depends on working flush/order primitives and tests crash/torn-write conditions. Filesystem structural recovery cannot compensate for a storage stack that lies about completion. SQLite's crash tests do not qualify Mycelium's reference/file publication order. |
| [Apple `fsync(2)`](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fsync.2.html), [`fcntl(2)`](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fcntl.2.html) | **D:** ordinary `fsync` can leave writes in a drive cache, including reordered writes. `F_FULLFSYNC` additionally requests a permanent-storage cache flush. These archived manuals explain the distinction, not a current APFS-specific hardware qualification. |
| [Apple File System Reference](https://developer.apple.com/support/downloads/Apple-File-System-Reference.pdf), “Container Layer” / “Mounting an Apple File System Partition” | **D:** APFS checkpoints and copy-on-write protect filesystem structure; mounting ignores an invalid interrupted checkpoint and chooses the latest valid one. This does not promise persistence of every application write or multi-file transaction after `rename`/`close`. APFS is not a substitute for application barriers. |
| [Go 1.25.6 Darwin `FD.Fsync`](https://github.com/golang/go/blob/go1.25.6/src/internal/poll/fd_fsync_darwin.go), [POSIX implementation](https://github.com/golang/go/blob/go1.25.6/src/internal/poll/fd_fsync_posix.go) | **C/D:** Go `os.File.Sync` uses `F_FULLFSYNC` on Darwin, falling back to ordinary `fsync` on `ENOTSUP`; Linux uses `fsync`. Therefore Go's helpers do **not** have the same macOS gap as Python `os.fsync` or SQLite's separate VFS. Fallback/nonlocal mounts remain unknown. |
| [Pinned modernc Darwin VFS](https://gitlab.com/cznic/sqlite/-/blob/v1.39.1/lib/sqlite_darwin_arm64.go), `_full_fsync` | **C:** the generated VFS calls `F_FULLFSYNC` only when its full-sync flag is set, otherwise `fsync`; failed full-sync also falls back to `fsync`. It does not call Go's `os.File.Sync`. Checked against the cached dependency source, not a running database. |
| [Linux `fsync(2)`](https://man7.org/linux/man-pages/man2/fsync.2.html) | **D:** syncing a file does not necessarily persist its containing directory entry. The directory needs its own `fsync`. Newly created ancestor directories also need their names persisted in their parents; syncing only the leaf is insufficient. |
| [Linux ext4 documentation](https://docs.kernel.org/admin-guide/ext4.html), `data=ordered`, `barrier`, `auto_da_alloc` | **D:** default ordered data mode and journal barriers preserve filesystem ordering subject to the I/O stack. `auto_da_alloc` mitigates common unsynced replace/truncate patterns; the kernel explicitly calls such applications broken. It is not a portable acknowledged-write guarantee. `data=writeback`, disabled barriers and device caches change assumptions. No actual mount settings were read. |
| [SQLite backup API](https://sqlite.org/backup.html), [VACUUM](https://sqlite.org/lang_vacuum.html) | **D:** online backup provides SQLite consistency, not a snapshot of Mycelium's separate files/authority. Ordinary VACUUM uses a journal/WAL when replacing the original. Interrupted `VACUUM INTO` output can be incomplete/corrupt; do not publish it as a completed backup. |
| [Linux CIFS implementation](https://github.com/torvalds/linux/blob/v6.12/fs/smb/client/cifsfs.c), [`nostrictsync` documentation](https://www.kernel.org/doc/html/latest/admin-guide/cifs/usage.html) | **D:** directory fsync is a no-op in this client; file flush and server-side guarantees still matter. A successful network filesystem call does not independently qualify the NAS controller's power-loss behavior. |

### Test boundaries and existing evidence to extend

**C:** existing tests include
[SQLite rollback/migration/reopen](../../internal/myce/queue_persistence_test.go),

and [installer returned-error rollback](../../internal/myce/install_preserve_test.go#L279).
These are relevant starting points, **not evidence of power-loss survival**.
They were read, not executed for this docs-only change. Extend these behaviors
rather than add parallel speculative scenario matrices.

**Proposal:** two distinct harnesses are needed. A subprocess kill-point harness
tests missing defers, cleanup ordering, stale attempts and restart behavior. It
does not discard kernel caches. A test-only durable-image filesystem/VFS model
must separately track volatile bytes and directory operations, persist only at
the required barriers, and rebuild a crash image while dropping or tearing
unflushed writes. Failed Sync must not advance durability. Include directory
creation/link/rename/unlink, nested ancestors and cross-file ordering, not just
short file writes. A simulated crash must stop further writes from the old
owner; returning an error while old goroutines continue is not a crash model.
Use actual SQLite VFS interception for Q1; a protocol fake alone cannot prove
SQLite WAL recovery. VM/block-device crash tests can later corroborate native
APFS/ext4 behavior on disposable storage, without restarting the development host.

Run each future targeted Go test directly, serially, with private scratch and
literal-path cleanup. Darwin/Linux laptop tests require no GPU, NAS, installed
service or fleet access. A later authorized physical drill is criterion 3 and
must not be represented as achieved by this inventory or by kill -9.
