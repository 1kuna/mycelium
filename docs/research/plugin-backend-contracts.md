# Extension contracts: what Mycelium should borrow

Research date: **2026-10-14**. For [research ticket #19](https://github.com/1kuna/mycelium/issues/19), feeding [map #17](https://github.com/1kuna/mycelium/issues/17). All external sources below are primary sources, accessed on that date; versioned pages identify the version surveyed, not a claim that it is the latest release. Recommendations are research judgments, not approved product behavior.

## Question

How do established systems define a stable contract for replaceable execution code? What must an author declare, how is compatibility checked, how do versions and packages move independently, and what happens when preparation or execution fails? Which patterns fit one mycelium of different hyphae, with extensions written once and shared through an extension library? [Ticket](https://github.com/1kuna/mycelium/issues/19), [map](https://github.com/1kuna/mycelium/issues/17), [vocabulary](https://github.com/1kuna/mycelium/blob/docs/mycelium-vision/GLOSSARY.md).

## Short answer

Recommend a small **versioned manifest plus ordinary executable commands**, with schema-checked inputs/results, exact package identities, a local compatibility check, and output qualification on each hypha. Keep resource accounting, attempt identity, stopping, and scheduling inside Mycelium. Borrow ONNX Runtime's work-specific support checks, Bazel's separation of execution and output requirements, Nix's explicit inputs, Ray's preparation lifecycle, HTCondor's requirements-versus-preferences distinction, and MCP's schemas and error separation. These are a synthesis of the cited findings below, not evidence that any one system supplies a universal execution layer.

The current approved design deliberately uses one Go binary, one SQLite queue, and ordinary commands, after v1 became too hard to use and test. Environment recipes already have input-based identities and bounded preparation; Docker execution is optional. The later vision expands to every resource, one common job description, and reusable extensions. This note proposes how to bridge those ideas without changing today's spec. [Approved design at the research baseline](https://github.com/1kuna/mycelium/blob/b989acc138fc160c60430855e415ea3846048b44/docs/design-proposal.md), [start here](https://github.com/1kuna/mycelium/blob/b989acc138fc160c60430855e415ea3846048b44/docs/START-HERE.md), [environments](https://github.com/1kuna/mycelium/blob/b989acc138fc160c60430855e415ea3846048b44/docs/environments.md), [vision decisions](https://github.com/1kuna/mycelium/issues/16).

## Findings

### 1. ONNX Runtime: describe support for the actual work

Execution Providers share the application API and report which graph operations/subgraphs they can execute through `GetCapability`. Selection is ordered; the documented CUDA-then-CPU example executes unsupported operations on CPU. This is graph-specific support, not a promise to run any program. [Execution Providers](https://onnxruntime.ai/docs/execution-providers/).

The newer external-library contract exports `CreateEpFactories` and `ReleaseEpFactory`; factories describe available hardware and create execution instances. Required fields include `ort_version_supported`, name, and support checking. Compilation or kernel registration supplies execution. Packaging guidance separates the extension library from core ONNX Runtime, suggests normal Python/NuGet packages, and requires a runtime version check with graceful failure. [Development](https://onnxruntime.ai/docs/execution-providers/plugin-ep-libraries/development.html), [packaging](https://onnxruntime.ai/docs/execution-providers/plugin-ep-libraries/packaging.html).

**Mycelium judgment:** copy support checking against the submitted work and independent distribution. Do not copy implicit CPU fallback: the vision explicitly disallows it for GPU work. A CPU resource can still run CPU work. A reported resource or successfully loaded library does not make an extension qualified on a hypha. [Vision decisions](https://github.com/1kuna/mycelium/issues/16), [glossary](https://github.com/1kuna/mycelium/blob/docs/mycelium-vision/GLOSSARY.md).

### 2. LLVM/MLIR: stable meaning needs explicit boundaries and maintenance

An LLVM backend describes a target through `TargetMachine`, registers, instructions, lowering, and emission, using C++ and TableGen. It is compiler implementation work, not simply a runtime selector. [Writing an LLVM backend](https://llvm.org/docs/WritingAnLLVMBackend.html).

MLIR conversion declares legal, illegal, or dynamically legal operations, rewrite patterns, and optionally type conversion. Full conversion succeeds only when all operations are legalized; analysis conversion can inspect what could be converted without rewriting. [Dialect conversion](https://mlir.llvm.org/docs/DialectConversion/).

LLVM's policy distinguishes interfaces: textual IR has no backward-compatibility promise; bitcode has compatibility tests and upgrade rules; the C API has best-effort stability. New official targets need broad tests and continued maintenance. MLIR's bytecode stability assumes unchanged dialect meanings; dialect authors can encode versions and supply upgrade hooks. Stable serialization alone therefore does not freeze semantics. [LLVM developer policy](https://llvm.org/docs/DeveloperPolicy.html#ir-backwards-compatibility), [MLIR bytecode](https://mlir.llvm.org/docs/BytecodeFormat/).

**Mycelium judgment:** copy explicit legal input subsets, a check before conversion, and compatibility fixtures. Package a compiler as a dependency behind an extension command when needed; do not make compiler internals the extension contract or require every author to build a compiler backend. These sources show concrete maintenance mechanisms, but do not establish why contracts endured as a historical causal claim.

### 3. Kubernetes: resource discovery and execution selection differ

Device plugins register a local gRPC endpoint, API version, and resource name; `ListAndWatch` reports inventory/health and `Allocate` supplies execution configuration. Optional functions are explicitly advertised. Deployment can use an OS package, manual installation, or a DaemonSet; restart requires registration again. Unhealthy hardware reduces allocatable capacity, but already assigned Pods retain their assignment. Hardware reporting does not itself recover work. [Device-plugin documentation, source updated 2026-09-15](https://github.com/kubernetes/website/blob/b4811b23fdc1a199b0d9754edf90579aa93b45de/content/en/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins.md).

The same documentation warns that the device-plugin API is not stable despite the surrounding Device Manager feature being generally available, and recommends handling multiple versions during upgrades. Feature maturity and interface stability are separate claims. [Device-plugin documentation](https://kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/).

RuntimeClass, stable since Kubernetes 1.20, maps a `node.k8s.io/v1` object to a preconfigured container-runtime handler. It selects execution rather than installing it. Scheduling restrictions and declared overhead affect placement; unavailable classes or handlers produce failure. [RuntimeClass documentation, source updated 2026-05-13](https://github.com/kubernetes/website/blob/c37d57216103cd3473e82dc7b481bf5b34a1a197/content/en/docs/concepts/containers/runtime-class.md).

**Mycelium judgment:** copy separate resource reports, execution requirements, and optional-feature declarations. Avoid requiring privileged per-resource daemons, Kubernetes deployment objects, or a second scheduler. A hypha owns its resources; an extension teaches Mycelium how to use some of them. [Mycelium vocabulary](https://github.com/1kuna/mycelium/blob/docs/mycelium-vision/GLOSSARY.md).

### 4. Ray: preparation is a lifecycle, not a hardware translator

Runtime environments declare files, packages, and environment variables for jobs/tasks/actors. Ray installs and caches them per machine, supports eager/lazy setup, and bounds setup with a timeout. Setup failure prevents dependent tasks/actors from starting and surfaces `RuntimeEnvSetupError`. Conda environments must match Python/Ray versions. Remote archives should reference a fixed commit; moving branches can produce different contents across machines. [Runtime environments](https://docs.ray.io/en/latest/ray-core/handling-dependencies.html).

Ray's actual `RuntimeEnvPlugin` hook offers validation, URI identities, creation, launch-context changes, and deletion. It imports Python classes, rejects duplicate names and invalid subclasses, and is marked `DeveloperAPI` under `_private`; no explicit protocol-version handshake appears in the inspected interface. This is useful implementation structure, not evidence of a stable language-independent contract. [Source snapshot, updated 2026-06-08](https://github.com/ray-project/ray/blob/08603fa400c8312449261fc6b6566e162e01b251/python/ray/_private/runtime_env/plugin.py).

**Mycelium judgment:** copy bounded prepare-before-start, immutable cache identity, and separate setup errors. Avoid a Python-only imported-class interface and assumptions that installing dependencies translates work to another resource. Existing Mycelium environment preparation offers a simpler starting point. [Current environments](https://github.com/1kuna/mycelium/blob/b989acc138fc160c60430855e415ea3846048b44/docs/environments.md).

### 5. Nix: explicit inputs and identity; do not overclaim reproducibility

Nix 2.28 derivations declare inputs, outputs, execution system, executable, arguments, and environment. The execution system must match the builder's system or extra platforms. Derivation serialization is content-addressed, but the manual distinguishes legacy ATerm encoding from an experimental changing JSON encoding. An input-derived identity is not by itself proof of identical outputs. [Store derivations](https://nix.dev/manual/nix/2.28/store/derivation/), [language contract](https://nix.dev/manual/nix/2.28/language/derivations).

Nix can export store objects and their references for import, providing a distribution mechanism separate from job meaning. Its build command distinguishes generic build failure, timeout, output-hash mismatch, and nondeterministic output in check mode. [Export](https://nix.dev/manual/nix/2.28/command-ref/nix-store/export), [build failure codes](https://nix.dev/manual/nix/2.28/command-ref/nix-build).

**Mycelium judgment:** copy explicit dependency closure, immutable identity, and differentiated failures. Do not require Nix on every hypha or depend on its experimental serialization. A package digest proves which bytes were used; output checks establish whether that extension is qualified for the intended work on the hypha. [Qualification meaning](https://github.com/1kuna/mycelium/blob/docs/mycelium-vision/GLOSSARY.md).

### 6. Bazel: where tools run differs from what they produce

Bazel 7.1 toolchains declare a type, a `ToolchainInfo` implementation, execution constraints, and target constraints. The consuming rule uses the resolved implementation without naming a particular compiler. Required toolchains fail analysis when no match exists; optional ones return no implementation. The type author must document the fields: arbitrary `ToolchainInfo` fields do not provide a shared schema automatically. [Versioned toolchain documentation](https://bazel.build/versions/7.1.0/extending/toolchains).

Bazel's module system distributes versioned projects, resolves dependency versions, and fetches source archives through repository definitions. This package versioning is separate from the meaning of a toolchain type. [External dependencies](https://bazel.build/external/overview).

**Mycelium judgment:** copy the distinction between the resource used to prepare an artifact and the resource required to execute it. Keep both internal to the extension plan so submitters do not write platform variants. Avoid transferring Bazel's rule language and dependency resolver into Mycelium merely to select an executable. [One common job description](https://github.com/1kuna/mycelium/issues/17).

### 7. HTCondor: requirements are gates; preferences rank eligible work

ClassAds describe work and resources with named attributes and expressions. `Requirements` constrain eligibility; `Rank` expresses desirability. Missing and invalid values have defined `UNDEFINED`/`ERROR` behavior. The documented transition to the new ClassAd library in 7.5.1 retained old exchange behavior through compatibility mode: an actual example of evolution without requiring immediate replacement of every participant. [ClassAd mechanism](https://htcondor.readthedocs.io/en/latest/man-pages/classads.html).

Execution can transfer an executable and declared inputs without a shared filesystem and retrieve declared outputs. A missing declared output puts work on hold. Missing executable/input errors also have a visible hold reason rather than indefinite blind retry. ClassAds select work; they do not supply a universal hardware execution implementation. [File transfer](https://htcondor.readthedocs.io/en/latest/users-manual/file-transfer.html), [job management](https://htcondor.readthedocs.io/en/latest/users-manual/managing-a-job.html).

**Mycelium judgment:** copy hard gates before preferences, explicit file inputs/outputs, and actionable failure reasons. Use a few typed fields rather than embedding a general expression language. Keep checkpoints and stopping under the existing attempt-specific rules, not extension-defined scheduling. [Current design](https://github.com/1kuna/mycelium/blob/b989acc138fc160c60430855e415ea3846048b44/docs/design-proposal.md).

### 8. MCP: good tool description, incomplete execution contract

The dated MCP 2025-06-18 specification defines tool names, descriptions, input JSON Schemas, optional output schemas, discovery, and calls. Protocol errors differ from execution errors returned with `isError`. Initialization negotiates protocol version separately from implementation version and optional features. [Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools), [lifecycle](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle).

Standard transports include local stdio subprocesses and Streamable HTTP; packaging is not part of the tool schema. The inspected tool/lifecycle contracts do not define Mycelium's resource accounting, durable execution attempts, checkpoint migration, or output qualification. [Transports](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports), [tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools).

**Mycelium judgment:** reuse JSON Schema and ordinary process I/O; consider an optional MCP-facing authoring interface later. Do not treat a tool description or successful call as resource admission or qualification. Adopting full MCP now would still require a Mycelium-specific execution lifecycle.

## Options and trade-offs for Mycelium

These are design judgments from the survey, not measured comparisons.

1. **Manifest plus commands — recommended.** A small declarative envelope describes supported work and resources; Mycelium invokes preparation and execution using its existing command runner. Authors can use any language. This fits current environment and process ownership machinery, but requires precise schemas, bounded outputs, and conformance fixtures. [Existing preparation](https://github.com/1kuna/mycelium/blob/b989acc138fc160c60430855e415ea3846048b44/docs/environments.md), [Nix process fields](https://nix.dev/manual/nix/2.28/store/derivation/), [MCP schemas](https://modelcontextprotocol.io/specification/2025-06-18/server/tools).
2. **Persistent local RPC extensions.** Useful if a demonstrated resource needs continuous observation or serving. Explicit negotiation and health reporting are possible, but supervision, reconnection, and ownership add complexity. Use as an optional execution form only when commands cannot meet a named requirement. [Kubernetes lifecycle](https://kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/), [MCP lifecycle](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle).
3. **In-process native libraries or imported classes.** Close runtime integration can suit a specialized engine, but couples authors to runtime interfaces and packaging. Keep ONNX/LLVM/Ray implementations behind the command boundary rather than using them as the common extension interface. [ONNX library contract](https://onnxruntime.ai/docs/execution-providers/plugin-ep-libraries/development.html), [LLVM implementation](https://llvm.org/docs/WritingAnLLVMBackend.html), [Ray hook](https://github.com/ray-project/ray/blob/08603fa400c8312449261fc6b6566e162e01b251/python/ray/_private/runtime_env/plugin.py).

## Recommendation for the next spec

Propose one author-facing contract, with optional operations rather than mandatory separate subsystems. The following details are recommendations for the orchestrator to resolve, not approved fields or implemented behavior:

- **Declare:** contract version separately from extension release and digest; accepted work/input/output schema versions; execution OS/architecture/runtime requirements; resource amounts and units; preparation inputs; commands; stop/resume support; and an output-check recipe. Require only operations the extension uses. This combines explicit requirements, package identity, and schema contracts. [Bazel](https://bazel.build/versions/7.1.0/extending/toolchains), [Nix](https://nix.dev/manual/nix/2.28/store/derivation/), [MCP](https://modelcontextprotocol.io/specification/2025-06-18/server/tools).
- **Check in order:** validate schema/version → inspect local resources/runtime → check this work's supported subset → prepare immutable inputs → establish qualification → admit and run. Return an explained wait when no eligible hypha exists. Qualification should bind extension digest, dependency identity, relevant local runtime/resource identity, workload scope, and reference outputs/checker. Changing these invalidates the corresponding record. No default lossy conversion or GPU-to-CPU fallback; disclose automatic conversion. The exact output tolerance must be resolved per work kind, not silently invented by an extension author. [ONNX support checks](https://onnxruntime.ai/docs/execution-providers/), [MLIR legality](https://mlir.llvm.org/docs/DialectConversion/), [vision constraints](https://github.com/1kuna/mycelium/issues/16), [qualified](https://github.com/1kuna/mycelium/blob/docs/mycelium-vision/GLOSSARY.md).
- **Keep ownership:** Mycelium allocates resources and owns execution attempts, cancellation, checkpoint locations, accounting, and confirmed release. An extension receives only its assigned execution context and reports structured outcomes. Distinguish unsupported work, preparation failure, work failure, infrastructure loss, failed output check, and unconfirmed cleanup; retry policy stays in Mycelium. Do not claim memory is free merely because a command timed out. [Current custody/attempt rules](https://github.com/1kuna/mycelium/blob/b989acc138fc160c60430855e415ea3846048b44/docs/design-proposal.md), [Ray setup failure](https://docs.ray.io/en/latest/ray-core/handling-dependencies.html), [HTCondor failure reasons](https://htcondor.readthedocs.io/en/latest/users-manual/managing-a-job.html).
- **Distribute simply:** start the extension library as versioned manifests and digest-addressed packages using existing repositories/package tools; include source, license, examples, and qualification fixtures. Install pinned bytes automatically for eligible work; do not execute a moving branch. Sharing a package never transfers its qualified status to another hypha. A spore should not be the only place retaining extension identity or evidence, but this ticket does not choose future coordination architecture. [Ray immutable-source advice](https://docs.ray.io/en/latest/ray-core/handling-dependencies.html), [ONNX packaging](https://onnxruntime.ai/docs/execution-providers/plugin-ep-libraries/packaging.html), [Bazel distribution](https://bazel.build/external/overview), [spore and qualification](https://github.com/1kuna/mycelium/blob/docs/mycelium-vision/GLOSSARY.md).
- **Make authorship testable:** provide one template and a laptop-only conformance command covering version mismatch, unsupported inputs, preparation failure, malformed results, cancellation, stale results, and cleanup uncertainty. Add work-specific output checks on the actual resource before calling an extension qualified. Defer new daemons, a custom package manager, and a compiler framework until a concrete extension requires them. [Simplicity requirement](https://github.com/1kuna/mycelium/blob/b989acc138fc160c60430855e415ea3846048b44/docs/design-proposal.md), [LLVM compatibility/test policy](https://llvm.org/docs/DeveloperPolicy.html).

**Why these contracts can last — bounded inference:** small shared meanings, independent implementations, explicit compatibility behavior, optional features, and maintained fixtures make evolution manageable. LLVM's compatibility tests, HTCondor's compatibility mode, and MCP's negotiation document mechanisms; they do not prove a single cause of longevity. Avoid a universal interface that promises arbitrary-program parity merely because it can describe arbitrary commands. [LLVM policy](https://llvm.org/docs/DeveloperPolicy.html), [ClassAd evolution](https://htcondor.readthedocs.io/en/latest/man-pages/classads.html), [MCP negotiation](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle).

## Confidence, limits, and current state

**High confidence** in the cited documented contracts; **medium confidence** that the command-based synthesis is the smallest sufficient Mycelium contract. This is an architectural recommendation, not a proven implementation or performance result.

No extension was executed, no experiment was run, and no resource or extension was qualified. I could not establish universal cross-resource compatibility, cross-platform checkpoint portability, the reliability of arbitrary third-party packages, or numerical parity from these sources. No exhaustive historical/version matrix or evidence of causal longevity was verified. Kubernetes's published device-plugin version matrix stops at 1.26; it cannot establish present compatibility. Ray's inspected extension hook and Nix's JSON derivation encoding have maturity caveats. [Kubernetes matrix](https://kubernetes.io/docs/reference/node/device-plugin-api-versions/), [Ray source](https://github.com/ray-project/ray/blob/08603fa400c8312449261fc6b6566e162e01b251/python/ray/_private/runtime_env/plugin.py), [Nix encoding](https://nix.dev/manual/nix/2.28/store/derivation/).
