# Detecting owner presence, power and heat

Research for [issue #25](https://github.com/1kuna/mycelium/issues/25), 2026-10-14. Research only; this note proposes choices for the [wayfinder map](https://github.com/1kuna/mycelium/issues/17), not a change to the approved product spec. All external sources below are primary sources, read on 2026-10-14; where no publication date is supplied, that is an access date, not a claimed publication date.

## Question

How can Mycelium tell, without special permissions, whether someone is using a hypha, whether it is on battery, and whether it is hot or loud? What should its defaults be on macOS, Linux and Windows/WSL2? [P1]

## Short answer

Use existing OS signals rather than inventing a presence detector: elapsed input inactivity, external-power state, and thermal pressure or trustworthy hardware alarms. These APIs exist, but their coverage and session scope differ. No source reviewed establishes a universal, permission-free measure of physical presence or audible noise. In particular, Windows' common temperature-probe class does not supply live temperatures. [A1–A4, L1–L4, W1–W4]

Proposed default: dedicated hyphae offer resources whenever awake; daily-use hyphae offer them after **five minutes left alone**, and laptops require **confirmed external power**. Owner activity or battery use withdraws the offer and interrupts Mycelium work. Use thermal signals where available, explicitly report missing coverage, and keep one optional per-hypha limit. This translates the agreed vision into a conservative starting policy; five minutes and the other numeric thresholds below are recommendations, not benchmark results or settled product decisions. [P2, P3]

## Findings

### What these signals mean

Input inactivity measures time without input, not whether a person is reading, watching a film, using a controller, or waiting for another program. Apple's API describes keyboard, mouse and tablet events; Windows reports input in the calling session; Wayland explicitly leaves activity interpretation to the compositor. Screen locking alone therefore should not grant permission to compute. Treat inhibition of idle/sleep as a useful additional veto where exposed, rather than treating an idle timer as proof of absence. [A1, W1, L2]

Recommendation: retain only a local idle duration and simple power/heat states. Do not collect key contents, window titles, application names, camera images or microphone recordings. None is needed for the proposed admission rule. This is a design choice, not an OS guarantee.

### macOS

- **Input:** `CGEventSourceSecondsSinceLastEventType` (Swift `CGEventSource.secondsSinceLastEventType`) returns seconds since an event; `kCGAnyInputEventType` covers keyboard, mouse and tablet input. `combinedSessionState` combines event sources in the current login session, not every user's session. Prefer a process in the owner's login session and an aggregate query, not an event tap or input recorder. Apple's reference establishes the query, but does not establish every current macOS permission/session configuration; permission-free operation and fast-user-switch behavior remain untested here. [A1, A2]
- **Power:** public IOKit power-source APIs distinguish AC, internal battery and UPS power. `IOPSCopyPowerSourcesInfo` plus `IOPSGetProvidingPowerSourceType` supplies the active source; `kIOPSNotifyPowerSource` reports changes. The header warns that discovering a battery at early boot can take seconds, so an incomplete initial read is not proof of AC power. Treat UPS battery operation as limited power too. [A3]
- **Heat:** `ProcessInfo.thermalState` is available on macOS from 10.10.3 and reports nominal, fair, serious or critical pressure. Apple says fair should reduce/defer background work; serious and critical reduce performance and call for reducing CPU/GPU work. This is a better default than reverse-engineering sensor registers. The documentation mentions fan behavior at elevated states, but the value is not a sound-level measurement. [A4]

### Linux

- **Input/session:** logind exposes manager, seat and session `IdleHint` and `IdleSinceHintMonotonic`. The latter is the time the hint changed, **not necessarily the last input timestamp**. Sessions update hints through `SetIdleHint`; session `CanIdle` identifies participation. Consume hints from relevant sessions, and do not assume that an unsupported or missing session is idle. A daemon and a desktop session have different integration needs. [L1]
- **Wayland:** `ext-idle-notify-v1` can report idle/resumed events for a seat. Its ordinary `get_idle_notification` respects idle inhibitors, including the protocol's example of a visible surface inhibiting idle; version 2's `get_input_idle_notification` ignores inhibitors. Prefer the ordinary, inhibitor-aware path for politeness. The protocol definition does not prove every compositor exposes it; feature-detect it. [L2]
- **X11:** the XScreenSaver extension exposes an idle duration in milliseconds via `XScreenSaverQueryInfo`. It requires access to the relevant X display and extension; it is not a Wayland-wide activity sensor. Neither an X display query nor a single seat's Wayland notification establishes activity across all sessions. [L2, L3]
- **Power:** UPower's read-only `OnBattery` reports whether the system runs on battery; property-change subscriptions avoid busy polling. This requires UPower to be present and reachable. A failed read must be unknown, not equivalent to its Boolean false value. [L4]
- **Heat/fans:** the kernel hwmon ABI specifies world-readable standard attributes, including optional temperature inputs, max/critical limits, hysteresis, alarms and fan readings. All attributes except the name are optional, and fault flags mean a reading cannot be trusted. Fan speed is a sensor quantity, not an acoustic guarantee. Use only clearly identified resource sensors with valid units/limits; never change fan controls, power limits or sensor permissions as a prerequisite. [L5]

Recommendation: start with logind/UPower and desktop-native idle detection when the hint cannot provide the required coverage. Do not read raw input devices or request elevated permissions merely to make a daily-use hypha eligible. If the installed desktop cannot provide trustworthy activity state, wait with a plain reason. Supporting another desktop is a bounded OS integration task, not a new scheduling system.

### Windows and WSL2

- **Input:** `GetLastInputInfo` is explicitly session-specific, not system-wide. Microsoft also warns that its input tick count need not increase monotonically, including synthetic `SendInput` events. Calculate durations with wrap-aware tick arithmetic and treat anomalous values conservatively. An interactive-session helper is a simpler first target than assuming a service in session 0 observes the owner. [W1]
- **Broader presence:** Windows power-setting notifications include `GUID_SESSION_USER_PRESENCE` for user applications and `GUID_GLOBAL_USER_PRESENCE` for services/session 0, the latter combining local and remote sessions. They offer presence states, not an exact five-minute input timer; do not equate their semantics with `GetLastInputInfo`. [W2]
- **Power:** `GetSystemPowerStatus` returns AC/DC state and battery information. `ACLineStatus` is 0 offline, 1 online, 255 unknown; `BatteryFlag` includes no-system-battery, while 255 means unknown. Battery saver is separately exposed and Microsoft recommends avoiding resource-intensive work when it is on. Do not infer external power from charging percentage alone. [W3]
- **Heat:** Microsoft documents that `Win32_TemperatureProbe.CurrentReading` is not populated in current WMI implementations. It is not a usable universal live CPU/GPU thermometer. No reviewed Windows source establishes a uniform, nonprivileged live temperature/noise API for all resources; driver/vendor-specific telemetry would need separate qualification. [W4]
- **WSL2:** Microsoft documents execution of Windows `.exe` tools from WSL with the active Windows user's rights, and that interoperability can be disabled. Proposed approach: a narrow query command in the Windows build of Mycelium, invoked through this established bridge, returning only aggregate activity and power states, without another resident daemon. Do not treat the Linux guest's idle/temperature observations as proof about the Windows owner or physical hardware. Session matching, bridge availability and actual invocation from an unattended WSL start still require verification. If the bridge is unavailable, a daily-use hypha stays unavailable; no administrator install or service should be silently required. [W5, W1]

### How established systems handle it

- **HTCondor:** its policy documentation distinguishes dedicated machines from shared desktops. The desktop example requires 15 minutes of keyboard idle and low CPU load before starting, then separates `SUSPEND`, `CONTINUE`, `PREEMPT` and `KILL`; dedicated examples use `START = True` and disable policy preemption. The document also describes publishing temperature through a custom script attribute, rather than establishing a universal built-in heat sensor. Lesson: separate admission from yielding and recovery, but do not copy a configurable policy-expression system into Mycelium. These are documented examples, not a claim that all installations ship with the desktop policy. [H1]
- **BOINC:** inspected source defaults have a three-minute idle threshold, GPU work disabled while the user is active, CPU work allowed while active, battery work disabled, and a 25% non-BOINC CPU-load suspension threshold. Its implementation checks power and activity and uses load hysteresis. The battery-temperature limit in the inspected suspension code is **Android-only**, not a general desktop CPU/GPU thermal guard. Lesson: power gates and recovery hysteresis are established patterns; distinguish input inactivity from other-program load and resource-specific policy. Do not copy all its preferences. [B1, B2]
- **Folding@home:** current v8 Bastet source has optional idle and battery gates that also block new allocations while unmet. Its group defaults are `on_idle = false`, `on_battery = true`, initially paused; therefore its current source does **not** justify claiming that it always avoids battery work. Its macOS idle predicate treats display off, login window, screensaver or lock as idle, unlike a fixed input-inactivity timer. Lesson: simple gates are possible, but these defaults and that idle definition are less conservative than the proposed Mycelium policy. [F1–F3]

These are dated source snapshots, not verification of installed releases. No universal desktop heat/noise policy was established from the inspected paths; BOINC's Android thermal handling must not be generalized. [H1, B2, F1–F3]

## Options and trade-offs for Mycelium

1. **OS signals plus a small availability rule — recommended.** Reuse the APIs above, with narrow platform integration only where the standard OS API needs it. Keep the queue's job model and existing interruption machinery. This gives understandable reasons such as “owner active”, “on battery”, “cooling down” and “activity unavailable”. It cannot promise that a motionless owner is absent or that an unsensed resource is quiet. [A1–A4, L1–L5, W1–W5, P4]
2. **Utilization-only detection.** Easy to imagine, but it does not satisfy the vision's “left alone” requirement: low utilization is not an input-presence signal, and counting Mycelium's own work would make availability self-defeating. Do not use it as the first admission gate. This is a policy inference from the requirement and the distinction between the documented input APIs and utilization. [P2, A1, W1]
3. **Rich per-application rules, privileged sensors or fan control.** Could add resource-specific refinements, but introduces more configuration and permissions without a verified cross-platform acoustic guarantee. Defer it; do not require it for joining. The reviewed optional Linux sensors and absent Windows WMI live reading illustrate the coverage problem. [P1, P2, L5, W4]

## Recommended signals and thresholds

Everything in this section is a **proposed policy**, grounded in the cited API semantics and vision, not a measured tuning result. Keep the decisions local to each hypha, then report its eligibility and reason to Mycelium. These are automatic thresholds, not a collection of user-facing knobs. [P2, P3]

- **Dedicated versus daily-use:** dedicated ignores owner-idle gating; daily-use requires five uninterrupted minutes of trustworthy inactivity. Require external power on every laptop in either mode. Read the vision's “idle or plugged in and left alone” as allowing idle desktops and requiring idle **and** power for laptops; plugging in never licenses disruption of an active owner. Sleep is respected; this policy should not wake a hypha or inhibit sleep. [P2]
- **Sampling:** use change notifications when available, backed by a five-second refresh. Mark required activity/power observations stale after 15 seconds or immediately on a known read failure. Re-evaluate from fresh state after wake or reconnect; elapsed sleep does not count toward the five-minute idle window. Five seconds/15 seconds are proposed latency/staleness bounds, not API guarantees. [A3, L1, L2, W2]
- **Owner returns:** stop admitting work immediately upon notification, or within the proposed five-second polling interval. Begin interruption locally so it does not depend on reaching the spore. New input resets the idle window. An unsupported or uncovered session means unknown activity, so a daily-use hypha waits. [A2, L1–L3, W1, P2]
- **Power:** no grace period for admitting work on battery. Withdraw current work on a battery/UPS switch. If a laptop's power state is unknown or stale, wait; a separately established batteryless desktop need not invent a battery requirement. On Windows, also defer during battery saver. A charging battery on confirmed AC is eligible; no minimum percentage is needed. [A3, L4, W3, P2]
- **macOS heat:** on daily-use hyphae, defer at **fair or higher** because Apple recommends deferring background work already at fair; resume only after nominal for 60 seconds. Dedicated hyphae may continue at fair but withdraw at serious/critical, then resume after nominal/fair for 60 seconds. This intentionally avoids a wattage or fan-control subsystem. [A4]
- **Linux heat:** withdraw on a trustworthy relevant max/critical alarm, or a valid reading at/above the resource's documented max; if only critical is known, propose a guard at **critical minus 10°C**. Resume only after every implicated sensor is below its guard by **5°C for 60 seconds**, using a valid supplied hysteresis value if more conservative. Do not apply a universal 80°C/90°C threshold to unrelated sensor types. The margins/dwell need later hardware validation; the kernel defines the attributes, not these Mycelium margins. [L5]
- **Missing heat coverage:** label it “heat sensing unavailable”, not “cool”. Initially allow work if the required owner/power gates pass, relying on the platform's existing management while making **no verified quietness or thermal-protection claim**. If sensing disappears during a known overheat hold, retain that hold until good readings return. Holding every Windows hypha forever for a missing thermometer would undermine the cross-platform goal; silently claiming thermal coverage would be worse. This is a conscious proposed trade-off for the orchestrator, not a settled vision decision. [P1, P2, W4]
- **Noise and the one optional limit:** do not claim a decibel threshold. Offer at most one simple optional **maximum simultaneous jobs** limit per hypha; absent that limit, preserve automatic filling by available memory. It can reduce concurrency, but one heavy job can still be loud. Do not add separate battery, fan, heat and idle tuning panels. [P3, L5, A4]
- **Running jobs:** use the existing checkpoint/interrupt/requeue path; do not promise that admission withdrawal instantly releases resources, or that an arbitrary GPU process can safely freeze. Propose a **10-second maximum checkpoint grace** for owner return/ordinary thermal holds, followed by stopping the attempt; on battery or critical heat, stop promptly rather than waiting through that grace. Non-resumable work may restart and lose progress, so placing it on a daily-use hypha must accept interruption. Planned politeness stops should not consume the infrastructure-loss retry budget. These are proposed semantics, borrowing the existing ten-second production preemption and planned-stop distinction. [P4]

## Confidence and unresolved verification

**High confidence:** the documented signal shapes and Windows session/WMI caveats; the vision requires laptop battery exclusion and part-time daily use. **Medium confidence:** the recommended small availability policy and five-minute wait. **Low/unverified:** permission-free coverage in every current desktop/session setup, helper operation from unattended WSL2, actual stop latency under GPU work, sensor mapping and heat margins, and subjective noise. [P2, A1–A4, L1–L5, W1–W5]

No programs were run to probe presence, power, temperature or performance. No hyphae were contacted, no fleet credentials were accessed, and no implementation, benchmarks or hardware experiments were performed. API documentation is evidence of contracts, not qualification on the target hyphae.

**Current state:** research complete on the dedicated `research/owner-presence-power-heat` branch, retained as a context pointer and never merged; the orchestrator retains the decision in #25. **Next step:** resolve the missing-heat trade-off and interruption semantics in the next spec, then separately authorize laptop-only tests of session scope, denied/missing signals, power transitions, stale observations and hysteresis with fake signals/Clock before hardware qualification. Do not interpret this note as authorization to change the current installation. [P1, P5]
