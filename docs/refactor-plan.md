# Refactor plan

Workstream 4 of [#1971](https://github.com/1kuna/mycelium/issues/1971). Start with exact-attempt custody. Run queue file-store ownership and the read-only part of status in parallel. Keep one Go binary, one SQLite queue and plain-command workers. Preserve the supported job, environment, checkpoint, model and fleet contracts in the [approved design](design-proposal.md) and [maintainer rulings](DECISIONS.md).

The maintainer asked to trim the repository and backlog before refactoring. The trim established the floor ([#1973](https://github.com/1kuna/mycelium/pull/1973), [#1975](https://github.com/1kuna/mycelium/pull/1975), [#1977](https://github.com/1kuna/mycelium/pull/1977), [issue triage](https://github.com/1kuna/mycelium/issues/1971#issuecomment-7115596662)). The next pass follows [#1972](https://github.com/1kuna/mycelium/issues/1972) and [#1982](https://github.com/1kuna/mycelium/pull/1982). Named incidents exposed a shared bad model, one pooled model replaced several mechanisms, and incident replays kept the behavior that mattered. That PR removed 30,442 lines net across the repo, including 5,049 runtime and 18,414 test lines in its changed internal Go files. The new estimates below budget replacement code and tests as that PR did. Memory, admission and placement changes belong to the r6.36 release owner ([#1983](https://github.com/1kuna/mycelium/issues/1983), [#1986](https://github.com/1kuna/mycelium/pull/1986)).

## 1. Exact-attempt custody

`attemptSupervisor.run` and `runAttempts` coordinate direct launches, detached adoption, stop, replay and result disposition. `runCustodian` also owns startup and stop delivery for detached processes. `recoverAttempt`, `cleanupOrphanCustody` and native-group recovery infer the next action from persisted process and group evidence. `fleetAdoptionReason` separately translates that evidence into a restart decision. Across these paths, a nil process, an inactive service, an accepted result and a release acknowledgement signify different facts. Recombining those facts in each caller makes restart and late acknowledgement branches multiply. In #1926 the launcher exited before Started and the attempt released, but cleanup discarded the evidence that could explain the exit. In #1792 successful publication left a stale finalization reason after release, and a different completed attempt still owed log replay. #1832 found that a stale launch authorization and a safe capacity refusal with exact release had different consequences. These observations point to split custody and publication state. The process exit cause in #1926 remains unknown.

**Model.** Derive the next action from one attempt record keyed by job, attempt and worker session, with the physical owner and its evidence attached. Carry two independent facts through the transition: whether execution still owns resources, and whether logs/results/checkpoints still need durable delivery. Assignment reserves custody. A platform adapter proves the manager handle, process birth and member identity before Started, adoption or signalling. Reconciliation distinguishes a live owner, positively proven release and unknown custody. Unknown holds the obligation. Stop intent, signal delivery, process exit, exact release acknowledgement and publication acceptance each have their own evidence. A commit can record more than one fact when the evidence supports it. The worker can publish after release, and the queue can stop charging resources on exact release while still retaining the files or process-free publication work. Fleet reads the resulting proof to authorize handover. Device-specific launch, process containment, resident engine lifecycle and file transfer keep their current contracts.

**First change.** The worker can begin in `worker_attempts.go`, `worker_custodian.go`, `worker_custodian_recovery.go`, `custodian_reconcile*.go`, `worker_recovery.go` and `attempt_outcome.go`. In the existing worker test harness, replay an exact-key pre-Started exit, an unverified detached process and a released attempt with a lost publication reply. Capture old decisions from the normal worker entry point. Make the direct and detached readbacks yield the same transition input, then route startup recovery through that function. Use the same release predicate in the live path in a second patch. Keep existing wire/spool fields as inputs while moving readers, and maintain the exact-write-before-effect sequence for launch, stop and replay. Positive evidence recovery still handles abrupt worker/queue death. Platform-native lookup and kill paths remain behind the same identity checks. Add a small adapter only if two consumers would otherwise translate the same proof independently. Queue-side adoption of the projection and deletion of the old branches can follow after the worker path matches its replay matrix. The internal scalar `attemptReply` wrapping a single assignment into a keyed directive is a later custody cleanup when its queue producer moves. It exists even between current peers.

**Deletion and replacement proof.** The scanned custody cluster has 5,129 runtime and 5,013 test lines in attempt protocol/outcome, worker attempts/recovery/custodian, native-group custody/recovery/cancellation and finalization. Target the alternate restart/stop derivations and duplicate terminal/result/release precedence, with a 900–1,500 runtime and 1,000–1,800 test line net budget over both patches. Extend `TestCustodianInitializedRecoveryRetainsUncertainCustody`, `TestCustodianStopDeadlineSurvivesAdoption`, `TestAttemptCleanupReleaseSurvivesRepeatedRestart`, `TestAttemptProtocolStaleResultByKey` and `TestFinalizationUploadRetry` into a fake-clock transition matrix, keeping distinct native checks for manager/PID birth and native groups. Add the #1926 scenario to the existing startup-diagnostics checks and the #1792 scenario to the finalization journey. Exercise cancel racing Started, sidecar/helper retention, independent failure before stop, exact release after process exit, queued retry after verified checkpoint, result/ack replay, stale attempt rejection and worker replacement with the same running process. Keep `TestCustodianNativeWorkerReplacement` and the signed upgrade journey through Linux and Darwin. Retire old cases when the matrix or real-process journey asserts the same decision and effects.

**Migration safety.** Begin with an in-memory view over the current spool. Run old and new derivations on the same saved input in tests, then switch one consumer at a time. Preserve spool read/write format through the adjacent release, exact-session ownership through restart, and fail-closed recovery on unfamiliar or damaged state. Prove process continuity, completion, portable checkpoint and release for a running attempt. If an existing attempt lacks positive identity after replacement, preserve its obligation and surface the evidence needed for recovery. Keep heavy I/O outside `q.mu`.

## 2. File-store ownership

`collectDurableFileReferences` already walks job, checkpoint, registry and upload facts. It returns three digest sets and can emit named keepers. `captureProjectFileHoldings` builds holder and physical-payload views from related facts. `fileReleaseMetadata` and `fileReleasePlan` build a hypothetical expiry and recheck collection eligibility. `projectFileFacts` combines current retainers with a different, deliberately rolling quota measure. The duplication is in how callers derive protection and explain it from these facts. In #1945 project-attributed bytes and bytes visible through a release selection could not be reconciled. Those readings included different populations, so the incident establishes an accounting gap, with some stale keyed replay retention reproduced. In #1917 the early plan fingerprint made unrelated changes to keeping references invalidate a review. Main already supports a narrower candidate set in `ApplyFileRelease`. Keep the surviving selection-refusal scenario as a replay and validate narrowing across claim, custody and publication changes. #1800 shows that transitive cancellation custody reaches content whose downstream use is undocumented.

**Model and first change.** Use one bounded, typed view of keeping references keyed by digest and actual owner. Capture committed reference identity under the existing queue lock and keep the existing lifecycle fence. Observe physical blobs, uploads and presence outside that lock, and recheck ownership and scope at apply/collection. Use the resulting facts for a project holdings answer and a dry-run release plan first. Live physical bytes deduplicate by digest, logical kept bytes may appear in several projects, and rolling historical additions remain a quota-policy calculation over their existing records. Unknown store availability, outstanding worker-local custody and parked retained state remain explicit and distinguishable from absent blobs. Feed the collector the same facts only after it agrees with the current collector on the same snapshot. Keep planned expiry idempotent. Its reviewed scope may shrink as protection grows, and widening requires a new review. Retain exact last-copy, publication age, upload and dependency fences. Start in `file_holdings.go`, `file_retention.go`, `file_release.go`, `file_input_claims.go`, `file_store_quota.go` and their tests. Reuse the existing custody query in the first patch. Defer any change in how downstream custody protects files until the maintainer rules on #1800.

**Deletion and replacement proof.** The ownership cluster has 2,659 runtime and 3,728 test lines across release, holdings, retention, quota, input claims, reclaim and GC. Target 400–700 runtime and 700–1,300 test lines net by retiring repeated holder, eligibility, and metadata derivations and merging repeated setup with shared real SQLite fixtures. Extend `TestProjectFileHoldingsAndCollectionAccounting`, `TestProjectFileHoldingsPrunedReplayDoesNotKeepReleasedInputs`, `TestFileReleaseReferenceChangeDuringCommit` and `TestFileReleaseSharedPublicationKeepsReviewedPlan`. Run holdings, plan, apply, dry-run collector and actual collector over one table of shared/cross-project content, active uploads, expired vs retained history, protected checkpoints, delayed output and unknown worker custody. Check size and digest deduplication, privacy, concurrent publication, narrowing and widening, and rollback after a failed transaction. ## Maintainer choices

1. **Release transition.** Keep adjacent-release rolling upgrades, or approve a synchronized exception after a later census proves savings that require it. Recommend keeping rolling upgrades. Retire the measured bridges with exact-pair and installed-config proof. Preserve retained-state readers.
2. **Storage reclaim scope.** Keep a dependent's transitive physical-custody protection for every selected parent file, or let terminal parents expire unrelated digests when the actual dependency graph proves those digests have no active consumers. Recommend the latter as a separately reviewed change after the shared reference view can demonstrate all keepers. Unknown and last-copy custody continue to block eligibility.
3. **Status consumers.** Keep existing JSON fields during the internal refactor, or plan a deliberate field retirement after verifying CLI, Python, skill and third-party use. Recommend field parity first and a follow-up only for demonstrated redundant fields. This keeps the read-path simplification independent of a consumer transition.
