# Mycelium

Mycelium runs CPU and GPU work for every project through one queue. It places each job among the currently eligible, qualified hosts using its implemented scheduling policy. You describe what the work **needs** and its **class**; you don't pick machines or negotiate with other projects for room.

## Submit

In short: run `myce spec check --resolve` first; the job's class is the only urgency lever; pin a host or device only for a hard requirement recorded in `requirement_reasons`; memory is optional.

1. Use the project's `.mycelium/adapter.yaml` entry (`myce run --entry NAME --key KEY`) or an existing profile (`myce run --profile NAME --key KEY`). For a one-off command, `myce run --cpu N -- CMD` (add `--gpu cuda|xpu|metal`; `--mem` is then accelerator memory and `--host-mem` host memory). Leave out `--mem` and Mycelium learns it. A one-off takes no `--key`, `--notify` or `--input`, so use an adapter entry when you need those. If nothing fits, author an adapter with [the adapter reference](https://github.com/1kuna/mycelium/blob/main/docs/adapter.md); [setup-project.md](setup-project.md) covers profiles.
2. **Resolve before submitting.** `myce spec check --resolve FILE` (a job spec with `--files-from DIR`, a profile, or `.mycelium/adapter.yaml` with `--entry NAME`) asks the queue, read-only, which machines can run the job as written. For each missing input or environment it names the field, the side that can't see it (submitter, queue or worker) and the fix. It also flags absolute data paths, system-Python commands, a host pin that only exists for data locality, and large tool bundles in the source. Apply those fixes instead of adding a pin. Nothing is submitted, uploaded, built or reserved, and submit revalidates.
3. **State needs, not machines:** platform, accelerator, cores, environment. **Memory is optional:** omit it and Mycelium treats the job as `memory: auto`. A CPU job's first run reserves a bounded exploratory envelope that doubles on OOM; on a unified-memory host, a plain GPU job without an accepted figure reserves only 1 GiB of device memory (the old `--mem` default) and a small host figure, and Mycelium cannot see the device memory it really uses, so declare a measured `--mem` (and `--host-mem`) for real GPU work there; on a discrete card the first run gets the whole card. Later runs reuse the accepted peak of comparable work. `myce status JOB_ID` and job GET `memory_envelope` show the figure used, its `basis` (declared, learned, hint or exploratory) and its `evidence` count. Job GET `resources` puts your declared figure, the learned one and the one used side by side for host memory, device memory, CPU and storage; once learned evidence covers a declared number, you can drop the number. Keep an explicit number only for a measured bound or a real containment need; Mycelium uses it as written. On a release with corrected discrete-XPU host attribution, a new accepted sample can lower an older inflated learned envelope: status then uses the maximum per-run host footprint, excluding sibling Mycelium growth. If a single accepted sample from a different GPU target/layout family produces a transferred host estimate above every allowance in a discrete-GPU target family, Mycelium permits one bounded measurement on that family’s largest eligible allowance, provided the measured peak plus 25% and any host hint fit. The cgroup total remains the conservative basis when complete evidence cannot separate reclaimable cache. The probe uses the allowance less launch slack and drift headroom, keeps live admission and release checks, and is consumed durably at assignment. Its next accepted target-family sample replaces the transferred prior. An OOM gets no probe retry; a constrained or otherwise ineligible result cannot reopen it, including after restart or resubmission. Reliable oversized peaks and OOM floors keep the actionable capacity refusal. A cold run is exploratory, not proof that a smaller reservation is safe. `myce portability` shows target, environment and qualification gaps; adding a variant still needs output parity before production use.

   Keep a host/device pin only for a hardware requirement, parity or validation, local-only data you can't yet stage, or a shared host that can run only an already-prepared environment. Record the reason in the adapter's `requirement_reasons`. For hardware or parity pins, qualify portable variants and verify output parity; for device validation, reserve only the device under test. Replace filesystem affinity with managed `source`, `files` or immutable `shared_inputs`; use the [queue-visible environment library](https://github.com/1kuna/mycelium/blob/main/docs/environments.md#queue-visible-environment-library) (`myce env list`, `myce env get NAME`) for runtime dependencies. Verify preparation and qualification before removing a pin.

   **Several GPUs:** write one entry with the job's total accelerator memory (`--mem`, `memory_gb` or `memory: auto`); Mycelium chooses the cards. Work one card holds gets one card; otherwise it gets the fewest cards of one host that hold it, all visible. Read the count from `MYCE_GPU_COUNT` (vLLM `--tensor-parallel-size $MYCE_GPU_COUNT`; Hugging Face `device_map="auto"` uses every visible card). Software limited to one device needs a job that fits one card. `require_target: true` refuses a need larger than any host's cards together.

   **Shared GPUs:** a GPU runs several jobs at once when their memory fits side by side, so an accurate `--mem`/`memory_gb` or an accepted `memory: auto` figure lets a small job start beside another instead of waiting. Managed Docker batch jobs can also share when their device figure is declared or learned and each container has an enforced host-memory cap. `run.docker_memory_gb` sets the main container cap independently of networking; without it the resolved host reservation supplies `--memory`. Sidecar caps or the shared parent still apply. Model-server, extension-check, fan-out, exploratory first runs and multi-card jobs keep their cards to themselves, as does a GPU job with `--host-mem` but no `--mem`. A newcomer never joins a higher class's attempt. A higher class stops the fewest co-tenants it needs (every co-tenant on its cards for a multi-card job) and starts after they release; the same class waits, and `myce status JOB_ID` says `device N shared with K attempts`.

   If fresh per-process samples show a shared card exceeds its memory budget, the lowest tier yields; among equals the job most over its reservation yields. This planned stop requeues without a failure, with each grower's measured peak × 1.25 retained as its next device-memory floor. Checkpoint grace and exact release still apply. Single tenants are unaffected. Missing or stale per-process samples cannot establish growth; a running job's reason reports when that evidence is unavailable.

   Shared interactive hosts admit only native CPU commands with already-prepared environments: no Docker, extension jobs or new environment preparation. Use a plain command via `myce run --cpu N --mem SIZE -- CMD` or a native command adapter entry with a prepared environment; work needing other execution modes waits for an eligible target.
   **External downloads:** declare `needs.network: true` on a CPU download job. Plain native commands default to unsandboxed in v1 and can use outbound networking without `native_network`; that capability qualifies protected outbound access for `isolation: sandboxed` jobs. A frozen extension retains its own isolation policy. Environment preparation and host CPU/RAM admission still apply.
   **Models:** declare the exact snapshot rather than asking for a mount or a download approval. In the adapter entry or batch YAML add `model_snapshots: {base: {repo: OWNER/NAME, revision: FULL_40_CHAR_COMMIT}}` (optional `files: [...]` allow-list) and read the read-only directory at `$MYCE_MODEL_BASE`, the same for native and Docker jobs. Mycelium verifies the snapshot from the fleet's shared hub cache and refuses with a named reason (`model_snapshot_missing`, `_revision`, `_mismatch`, `_escape`, `_too_large`, or `model_snapshot_not_permitted` at submit). For a missing snapshot, run a CPU job with `needs.network: true` that runs `hf download OWNER/NAME --revision COMMIT` into the shared hub cache, then resubmit. A `not_permitted` refusal is local queue policy: propose the source to the Mycelium thread. Pass offline flags (`HF_HUB_OFFLINE=1`) and load from the path; see [declared model snapshots](https://github.com/1kuna/mycelium/blob/main/docs/files.md#declared-model-snapshots-553).
4. **Choose a class:**

   - `production`: work your project's rulings call production. Under the current policy it ranks first and can stop lower-tier work, including non-resumable commands.
   - `deadline` with `--deadline <RFC3339>`: work with a real date that Zach or a ruling set. It can stop lower-tier resumable work after a grace period; non-resumable commands keep running.
   - `experiment` (the default): everything else.

   Equal-tier work is never stopped to make room, a running job isn't migrated, and eligibility, resources and locks still apply, so a higher class doesn't guarantee immediate capacity. A higher class than the work deserves takes capacity from someone else's real deadline.
5. `git: HEAD` sends committed bytes only: commit first, and ignore `.mycelium/receipts/`. Save the receipt's `key` and `job_id`. The same key recovers the same job after a lost reply; changed intent needs a new key.
6. Make long experiments resumable: implement [atomic checkpoints](https://github.com/1kuna/mycelium/blob/main/docs/files.md) through `MYCE_CHECKPOINT_DIR`, restore progress on restart, then declare `resumable: true`. The flag alone does not preserve progress.

## Wait and check status

- For an adapter or profile submission, bind completion to **your own** thread with [t3-binding.md](t3-binding.md) and pass its notifier as `--notify`. One binding per submitting thread, never an orchestrator's or a shared one. For a one-off, wait with `myce wait JOB_ID` (exits 0 only on success); it retries queue outages, and after two minutes without a successful read it logs where it is blocked and reconnects with the installed authority. Check the installed CLI's usage line before relying on a flag.
- **Available from the next release:** host headroom credits fresh exact-attempt nonreclaimable cgroup memory from managed Docker containers, including jobs without a shared cgroup parent. Missing or five-second-old samples keep the full reservation, and unified CUDA keeps its device-growth floor. External-memory history excludes this sampled container memory; a running container without a fresh sample makes that observation unknown.
- Read one job at a time: `myce status JOB_ID` (with its attempt history), `myce logs JOB_ID`. The full `myce status` snapshot is large and slows the queue for everyone, so keep it out of loops, checks and briefs.
- Give a long job one stall check at about twice its expected duration, bound to your thread, verifying one thing (the job's state or log growth), and delete it when done.

## Results

`myce result JOB_ID --out DIR` verifies each output's SHA-256 and size; then run your project's own acceptance check, since a wake or a zero exit proves no result. Download within the retention window (default seven days). The queue store is shared: write large outputs (hundreds of MB and up) to your project's own storage inside the job and return a small receipt (path, size, SHA-256) as the result. Once you have collected and verified results, release them with `myce file release plan --project P JOB... > PLAN.json`, review the plan, then `myce file release apply --accept-expiry PLAN.json`; on `file_release_stale`, plan and review again, then apply promptly. A project may have store quotas: an over-quota non-production submission is refused with `project_file_store_quota` and a reason giving usage and limit, and resubmitting the same key works after a release or once the 24-hour allowance frees. Production work is never refused by quota. Failed jobs have no accepted outputs; `myce result JOB_ID --attempt N --out DIR` fetches failed-attempt diagnostics. Report placement as "Mycelium placed it on X because Y", from the job's placement rationale.

**Release results early** to free shared store space once your project is completely done with them, rather than waiting out retention. Select only your own project's terminal jobs, after every downstream use has finished and any copy you must keep is saved and verified; include fan-out parents, children and keyed answers you want expired. The project name is attribution, not a permission check, so never select another project's jobs. Plan, review, then apply:

```sh
myce file release plan --project P JOB_ID... > release-plan.json   # read-only snapshot
myce file release apply --accept-expiry release-plan.json          # irreversible
```

The plan lists each job's files, what still protects them and `reclaimable_bytes` (it can be zero while still expiring your references). Apply rechecks the plan: `file_release_stale` means re-plan and review again, nothing was expired; `file_release_protected` means a selected job is still live, has unresolved custody or lacks a verified delivery, so drop it from the next plan. Success schedules asynchronous collection, so freed space isn't immediate, and the released results then return `result_expired`. Keep the plan and apply response as your audit record. API: `POST /api/files/release/plan` and `/api/files/release/apply`; see [operations](https://github.com/1kuna/mycelium/blob/main/docs/operations.md#project-owner-early-file-release-465).

## Urgency and pausing

- **Urgency is the class.** When your work must go first, submit it with the class it truly has and read its waiting reason. A message asking another project to stop can't change queue order, and their queued jobs would take the freed slot anyway.
- **Class is the only urgency lever.** Production class preempts lower tiers; nothing else reserves machines except a job-bound validation reservation for a qualification check. There are no customer windows or holds. Pins, holds and messages to other projects are not ways to go first.
- **Isolated checks:** use a job-bound reservation, not a higher class or a chat-negotiated hold. `myce extension check --reserve` reserves its selected device (the whole host for a CPU check); for an existing single validation job, use `myce reserve add SELECTOR --job JOB_ID --owner OWNER --reason TEXT`. For GPU extension checks, `reserve add host=HOST` defaults to the check's explicitly selected device; use `--whole-host` only when the check needs host-wide isolation and explain why in `--reason`. Other validation jobs retain their authored scope. Prefer `host=HOST;devices=DEVICE` when only one device needs isolation, leaving siblings eligible; quote the selector in the shell. Reservations withhold new conflicting work while started work finishes, and release after the bound job finishes and cleanup is confirmed; they do not guarantee immediate capacity. See [validation reservations](https://github.com/1kuna/mycelium/blob/main/docs/operations.md#reserve-a-host-or-its-devices-for-an-existing-validation-job). Broader policy changes stay with the queue owner.
- **Pausing your own queued job:** `myce pause JOB_ID --reason TEXT` makes it non-runnable (add `--until RFC3339` for an automatic resume time); `myce resume JOB_ID` restores it with the same key and queue age. Assigned/running attempts cannot be paused; leave running jobs alone. Don't cancel and resubmit paused work.
- Queue policy (`myce policy`) is shared state: propose a change to the Mycelium thread rather than setting it.

## When a job waits

1. Read its waiting reason: `myce status JOB_ID`. From the next release, reasons name reservations only on compatible targets, give the resolved RAM envelope against each eligible host's free memory, and explain missing protected network support or disallowed environment preparation. Device reservations permit CPU work when the host's RAM and cores fit. Repeated owner-latency preemptions on a shared host trigger a job-specific cooldown there; other eligible hosts remain available. A missing configured NAS mount names the affected root role and holds only work depending on it; healthy local/cached work can continue, and admission recovers automatically when the mount returns. Every waiting job has one: missing qualification, memory or resource needs, no available host, software preparation, or work ahead in the queue. GPU batch-slot contention can show up as a memory reason (mycelium#537).
2. Fix what's yours, in order: right-size needs using comparable accepted evidence, add portable targets, make the job resumable, and choose `deadline` plus a real date only when warranted. Submission, status and wait replies include deadline guidance explaining policy precedence, blockers and ETA uncertainty. This is advice, not a deadline guarantee or an edit to accepted job intent; for an existing job's urgency, ask the queue owner rather than cancelling and resubmitting it.
3. Otherwise it's a hold with a next owner: record it on your ticket and keep other work moving. Running heavy work locally on a shared host instead isn't a fallback.
4. If the reason looks wrong, or Mycelium itself failed, search the Mycelium issues for a duplicate, then update or file a sanitized one (expected versus observed, version, job and attempt id, minimal command). The repo is public: no secrets, private paths, host details or webhook URLs.

## Credentials

`myce submit FILE` also uses installed credentials when `MYCE_TOKEN` is unset, including the installed queue address and TLS pin.

Never open, print, copy or pass fleet credentials, and never set the fleet token yourself. Use the installed-authority CLI or `Client.from_installed()`, which resolve credentials internally; prefer the CLI for read-only status and result calls. A missing CLI or failed authority is a setup hold, not a reason to look for the token.
